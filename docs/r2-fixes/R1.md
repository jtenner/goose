## Change and scope

`Binary::Check` sends `==` and `!=` to `CheckEquality`. This helper saves entry flow, then checks the left and right operands in source order. Where `CheckBinaryResult` must convert arrays to slices, it restores entry flow before it checks both adapted operands in the same order.

The second pass is required by the existing storage checks. A fixed-array value that was copied can become a retained slice view. A later operand must not shrink the storage that view uses. Removing the second pass would break `shrink_temporary_implicit_slice.goose`. The fix keeps this rejection and adds the matching `!=` control.

The three changed product files are `src/typecheck.h`, `src/typecheck_nodes.h`, and `src/typecheck_exprs.h`. The change owns equality adaptation. It changes no parser, code generator, runtime, call inference, or other finding. Equality shares entry dispatch with scalar, optional, composite, and array checks, so the focused checks include existing equality and flow fixtures. Other binary operators keep their checking behavior, with one additional equality dispatch test. The new helper keeps the flow snapshot out of the `Binary::Check` stack frame used by other operators.

## Cost and measurement handoff

The changed performance path is compiler typechecking of `==` and `!=`. It is shared by scalar, optional, composite, array, and slice equality. No code generation or runtime source changed, and the fix adds no runtime operation.

Every equality now saves flow before checking its operands. `SaveFlow` copies the variables visible through named frames, scans global definitions for narrowed globals, and copies active kill records. The local snapshot has inline capacity for 16 entries, and named-frame discovery has inline capacity for eight frames. The snapshot adds constant stack storage and a helper call frame while equality operands are checked. More visible variables, narrowed globals, kill records, and frame-discovery data can require heap allocations. This adds work and memory that scale with visible state. When adaptation occurs, restoring flow also scales with that state. Both adapted operands are checked from entry; this can repeat a left slice check where the previous code repeated only the right operand. Those checks can scale with operand size and callee work. There is no new generated runtime allocation or copy.

The snapshot is needed before either operand runs because either operand can assign a local or change narrowing. It preserves the current second-pass storage checks without adding a new effect journal or changing shared provenance rules. Its cost needs measurement before landing. No runtime, memory, allocation, or code-size gain is claimed.

- Same-type array equality and slice equality, which save flow but need no adaptation.
- Different fixed-array lengths, array versus slice in both directions, and non-fixed array kinds.
- Equality in nested functions, branch-heavy code with narrowing and kills, and a large compile workload with many comparisons.
- End-to-end compile time, peak memory and allocations, plus compiler code size. Compare generated C identity and runtime controls. Run no invalid R1 program on the baseline as a runtime performance workload.
