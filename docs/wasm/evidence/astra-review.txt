Independent scalar Wasm review

Base: upstream/master 7b90f91d91845f4ef1712e16ed053f395e4e6e1c.
Reviewed uncommitted source. No repository source edits, no subagents, no Claude, and no performance timing.

Confirmed findings

1. P1: Null comparison reads a narrowed optional's pointee instead of its address.
Location: src/wasm_codegen.h:289-304, with Gen(Ident) decay at 398-404.
Valid trigger:
fn main() { var a=false; let p:bool?=&a; if p { print(p != null); } }
Native stdout: true\n. Wasm stdout: false\n. Both backends exit zero. This occurs at O0 and O2. Replacing bool/false with i64/0 causes emitted Wasm validation failure: i64.ne expects an i64 right operand but receives i32.const. Null on the left, such as null != p, is wrongly rejected as an unsupported value layout before output. Floating optional null tests also select float comparison opcodes for i32 addresses.
Evidence: results2.json and results3.json; narrowed_bool_null.goose and corresponding native/Wasm artifacts. C backend dedicated null handling in src/codegen_nodes.h:179-209 reads the declared reference slot even if the expression type has been narrowed.
Risk: Silent wrong control decisions in supported scalar code; other legal comparisons emit invalid modules or fail compilation.
Suggested fix: Lower null comparisons before general scalar operands. Generate null as i32 zero and read a variable's reference address without decay. Handle either operand position. Test == and !=, both null positions, before and after flow narrowing, and bool/int/f32/f64 pointees at O0/O2.

2. P1: Floating reference identity chooses a float comparison instruction.
Location: src/wasm_codegen.h:289-298.
Valid trigger:
fn main() { var a=1.5; var b=2.5; let p=&a; let q=&b; print(p .== q,",",p .!= q); }
Native stdout: false,true\n. Wasm compiler succeeds, but Node rejects the emitted module: f64.eq expected f64, found local.get of type i32. O0/O2 both fail. The f32 form also fails with f32.eq on an i32 address. Even p .== p with a null f64 optional fails validation.
Evidence: results.json, results2.json, results4.json; float_ref_compare.goose, float32_ref_identity.goose, null_identity.goose and emitted artifacts.
Risk: Legal scalar reference identity programs cannot run.
Suggested fix: Handle .== and .!= as address comparisons before pointee-type arithmetic selection. Keep the declared reference address semantics used in src/codegen_nodes.h:123-144. Test equal and distinct objects, both float widths, optional nulls, and int/bool controls.

3. P2: Scalar reference rebinding reaches arithmetic lowering.
Location: src/wasm_codegen.h:501-508 and 520-527.
Valid trigger:
fn main() { var a=1; var b=2; var r=&a; r .= &b; r += 3; print(a,",",b,",",r); }
Native stdout: 1,5,5\n. Wasm rejects the valid program with 'wasm target: arithmetic needs a scalar numeric type' at O0/O2. AssignOp leaves T_DOTASSIGN unchanged, and Assign treats every operation other than T_ASSIGN as arithmetic.
Evidence: results.json and rebind.goose artifacts. C backend handles T_DOTASSIGN as GenRebind at src/codegen_nodes.h:876.
Risk: Ordinary scalar aliases cannot be rebound despite support for plain scalar references. The diagnostic describes an arithmetic problem rather than the missing reference operation.
Suggested fix: Handle scalar reference rebinding as a direct write of the RHS reference address, without loading the old pointee or invoking Arithmetic. Keep '=' writes through a reference and '.=' writes to its slot distinct. Test rebind followed by mutation, optional reference to null/non-null, reference assignment RHS evaluation order, and O0/O2.
