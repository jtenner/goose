The design checks gave these results:

- `src/value_layout.h:32` defines the packed prefix separately from a growable owner's private header. Runtime-limited arrays have u32 capacity at offset 0, u32 length at offset 4, and elements at offset 8. Fixed arrays have no length field. Static limited and variable arrays retain their existing length widths. `LenStore` still requires a static capacity for limited arrays. The new runtime branch returns before calling it. Growable header accesses still use their separate base/length schema.
- The three changed C emission paths in `src/codegen_construct.h:86`, `src/codegen_construct.h:1240`, and `src/codegen_values.h:381` use the shared length and element offsets. Their callers select the runtime representation before reaching them. Static limited values keep their native C value path. I verified 34 exact generated-C pairs in the compatibility records. I also compared all eight new fixture C files against the prior compiler's saved C, replacing only each exact source path. Each pair then matched. This provides direct evidence that the changed C text is preserved for these cases.
- `src/wasm_codegen.h:49`, `:92`, and `:255` keep owner pointer slots separate from packed value bytes. A runtime-limited reference denotes the data header, not its local or global pointer slot. Ordinary stored references remain eight bytes. Runtime-limited reference values use i64. References to inline arrays still use Memory 0 addresses. Type discovery follows reference interfaces even when no owner exists. The saved no-owner O0 module has one memory and an i64 `inspect` parameter. It adds no data memory.
- `src/wasm_arrays.h:75` evaluates capacity once into an i64 local before reservation. The unsigned comparison against UINT32_MAX rejects negative signed values, all larger unsigned values, and signed positive overflow of the capacity range. The next comparison checks `(UINT32_MAX - 8) / stride` before multiplication or truncation. Admitted scalar and ordinary-reference strides are nonzero. The checker requires fixed-size elements and rejects zero-size elements; Wasm rejects unsupported compound and relative layouts. `Reserve` adds the existing top in i64 and rejects an exclusive end above UINT32_MAX. Offset zero remains reserved. Thus the capacity byte-count check alone does not claim that every accepted count fits at every current top.
- `src/wasm_memory.h:46` publishes the top only after growth succeeds. The new owner pointer and metadata are written after reserve returns. The metadata writes contain no source calls. Whole-capacity reservation prevents later push operations from moving existing element addresses. Pop and clear change length only for limited arrays. The allocation-failure fixture fails before reservation; the separate hard-limit helper fixture checks real memory.grow failure and preservation of top, contents, and another memory.
- `src/wasm_memory.h:101` uses `uint64_t(offset) << 8 | opcode`. This retains every u32 offset bit and the opcode. `WasmBytes::Mem` encodes the offset as a memory-instruction immediate, so it cannot carry into the packed memory identity. Dispatch checks the identity first. Effective-address bounds remain engine checks. I decoded separate saved load helpers for offsets 0, 4, and 16777216, plus the offset-4 store, across Memory 0, 1, and 2. The helper indices are distinct. Zero-offset names and encoding remain unchanged in the 76 prior module comparisons.
- `src/wasm_arrays.h:349` captures the receiver and evaluates the pushed value before reloading current length. Capacity comes from its own field. It stores the item before increasing length. Indexing captures length before an effectful index, uses an unsigned bounds comparison, and checks the element address. Equality compares length and live elements, so unused capacity does not affect it. Iteration reloads length and mutable reference paths. The fixtures cover direct mutation, by-reference iteration, stored scalar references, a rebinding array-reference element, different capacities with equal values, float/bool elements, and stable element aliases.
- `src/wasm_storage.h:41` reserves an owner's logical index before visiting its initializer. Calls made by a capacity expression or initializer therefore use a base above the owner. This is conservative but prevents overlap. Conflicting call bases use a dynamic base parameter. The values fixture calls the same allocator with different live-owner counts. Global owners use distinct persistent memories. Borrowed calls/results retain their packed address. By-value array parameters, results, copies, whole-array assignment, and unsupported temporaries still have explicit rejection paths.
- `src/wasm_codegen.h:309` emits cleanup actions in reverse order. A defer runs at its registration position among owner restores. Return values are captured before cleanup. Break and continue restore the exited scopes. The cleanup fixture exercises normal exit, early return, break, continue, nested deferred owners, and calls from defers. The source plan places deferred owners above the block's owners. Terminal host failure is not evidence of general guest stack unwinding; I make no such claim.

That is visible in the artifacts; it does not establish a runtime regression.

Capacity-only construction emits a fixed amount of bookkeeping per source constructor, independent of the runtime capacity. Its guest reservation is `8 + capacity * stride`. It does not emit a loop that initializes unused elements. Engine growth can still have capacity-dependent cost. Push, pop, clear, length, and capacity use fixed work per operation in this scalar scope. Equality and iteration scale with live length. Fills execute one value evaluation and a loop over count; strings copy their byte count. Byte printing takes host snapshots, so it copies and allocates in proportion to the printed live bytes. Multiple pending arguments can retain multiple snapshots. Those host costs already belong to the byte-print path and apply to the newly admitted arrays too.

Explicit-literal emission scales with source element count. `InitDataArray` reuses its item local; it does not add constructor scratch locals per literal element. Element expressions can still add their own locals and code. I parsed the saved 14,000-element variable-array module: 230,812 bytes and maximum 16 locals at both levels. The 9,000-element variable-array module is 162,788 bytes and maximum 16 locals. These use the same constructor loop, but they are not runtime-limited scaling runs. A runtime capacity value alone does not cause capacity-sized compiler allocation. Strings, source ASTs, emitted code, and diagnostic path strings still scale with their source representation.

The access cache now stores a 64-bit key instead of a 32-bit key. This increases key payload and can increase map-node padding/allocation size. Exact allocator bytes were not measured. There is one cached function per distinct opcode/offset, not per element, runtime capacity, or access execution. In the present production paths, new nonzero offsets are the u32 length load/store at 4. Each emitted dynamic helper has one arm per physical memory, so helper emission and code storage scale with helper count times memory count. Runtime dispatch uses br_table; no timing result is implied. The shared storage accounting follows the call graph, and base propagation queues a function at most twice. Conservative lexical ownership, including initializer calls and deferred code, can still increase the memory count.

Each data memory starts at one page. Empty runtime-limited owners reserve an eight-byte header but can require a separate physical memory slot. The values owner checks assert one-page buffers after 10,000 scoped uses. Since Wasm memories do not shrink here, this also bounds their observed guest buffer high water in that run. The bytes owner check establishes growth to at least two pages in a data memory and restoration of scoped tops. From the inspected capacities and source, the expected aggregate guest buffer size is 458,752 bytes, including Memory 0; the harness does not assert that exact aggregate. Cleanup restores tops but does not return grown pages. Globals retain their reservation. The 64-data-memory limit bounds the number of slots, not aggregate payload capacity. Per-memory page rounding and separate historical maxima can retain much more guest address space than the currently live values need.
