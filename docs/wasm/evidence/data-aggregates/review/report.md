**Correctness and design assessment.** The following conclusions are based on source inspection and the selected saved evidence, not a new execution:

- Admission remains limited to ordinary u32-count variable arrays with positive fixed nominal elements. Fixed-layout support rejects nonfixed owning fields and the guarded array forms. By-value aggregate calls/results, data iteration, aggregate fills/capacity, general replacement/adaptation, and relative/pool/root/slice forms retain guards. Layout and header helpers were not changed.
- `ReserveFreshDataArray` checks the planned owner and initialization, positive stride, four-byte prefix, and total span. It uses a 64-bit count bound before narrowing. It reserves and registers the complete owner before prefix or child stores. Whole copies capture the source and length before reservation and copy the header plus payload into a separate owner. Empty owners still have independent identity.
- The constructor proof is attached to a checked fresh owner with a complete reserved extent. `FreshDataElement` and `FixedChild` check their subspans. General `ResolvePlace` does not grant that proof to a borrowed address. Packed address displacement is used only after these bounds checks, so the child offset cannot carry into the memory selector for an admitted image.
- Storage planning keeps callee data storage above live caller owners. Scope exit paths restore owners in reverse order; function exits also restore the frame. The cleanup fixture covers partial construction, return, break, continue, nested calls, and a live outer owner. References remain shallow, while whole-copy owners remain distinct.
- Shared push/fill scratch is written after nested initializer evaluation. Scalar scratch is split by Wasm value type. Function entry resets these caches. Mixed types, nested initializer effects, strings, defaults, and zero-count fills have relevant tests. Checked field ordering rejects effectful source-order changes before this backend's field-order emission.
- Known and unknown memory copies preserve the actual memory identity. The new fill helper checks the selector and emits the operation for the selected memory. Helper reuse is bounded by the module's memory identities. Maximum-memory fill execution remains a coverage limit below.
